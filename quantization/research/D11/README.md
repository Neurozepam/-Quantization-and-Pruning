# День 11. Представление весов или алгоритм поиска?

После отрицательных результатов D10 я разделил две причины проигрыша: недостаточную выразительность формата и недостаточно хороший подбор кодов. Заодно проверил новую гипотезу взаимодействия кодов и смешивание каналов в gated MLP.

## Более сильный encoder

Ввёл E0 — известный локальный поиск с полной матрицей H, а не только её диагональю. Это контроль, не новый метод и не глобальный оптимум. На фиксированной панели двух моделей, трёх калибровочных подмножеств и четырёх форматов завершены 288 матричных кодирований.

Калибровочная энергия ошибки снизилась примерно на **42–67%** относительно D10. Основной эффект дал пересмотр кодов с полной H; дополнительная подгонка таблиц обычно добавляла лишь 0.06–0.21%. Значит, часть прежнего проигрыша действительно связана с encoder, но разрыв между форматами полностью не исчез.

Для OPT-125M успел проверить полную модель на subset0:

| Рецепт | PPL |
|---|---:|
| Нативный GPTQ | 28.2680 |
| E0 trellis | 28.2837 |
| E0 window_mirror | 28.0275 |

Window лучше GPTQ примерно на 0.85%, но это одно калибровочное подмножество, без полного набора ближайших контролей. Полное подтверждение по трём подмножествам из этого не следует. В первоначальном ограниченном цикле пара полных Smol-запусков не поместилась в оставшееся время; позже её выполнил в отдельной локальной очереди.

## Взаимодействие трёх кодов

Проверил H1: к обычной сетке добавляется общая таблица взаимодействий трёх 4-битных кодов с направлением из калибровочной H. Для сравнения использовал более свободный контроль, инициализированный точно из кандидата.

Завершены 72 кодирования на 36 матрицах. Прототип не прошёл калибровочный отбор на обеих моделях, поэтому полную PPL для него не запускал. Проигрыш нельзя целиком приписать форме представления: сходимость поиска и выбор host также не изолированы. Этот рецепт продолжать без новой причины не вижу смысла.

## Локальная проверка смешивания каналов

Следующая гипотеза — совместно менять up/down-веса gated MLP с учётом gate. Это не точная симметрия сети: отдельно учитывал изменение FP-выхода и ошибку квантования.

На девяти участках проверка на резервных калибровочных данных не пройдена. Относительно сохранённого варианта улучшение было, но относительно identity-контроля кандидат в среднем оказался хуже примерно на 1.9%. Полные PPL-диагностики кандидата не выполнялись.

В этой же локальной очереди известные E0-контроли на Smol subset0 дали PPL **16.9524** для trellis и **16.9942** для window_mirror. Это результаты отдельного этапа, не средние по трём подмножествам и не доказательство нового метода.

## Вывод

Сильный encoder оказался важнее многих изменений сетки. Дальнейшие идеи нужно проверять с общим full-H поиском, сопоставимым host и полным учётом памяти. При этом снижение локальной ошибки ещё не гарантирует улучшения PPL.

Подтверждённого нового метода пока нет.
