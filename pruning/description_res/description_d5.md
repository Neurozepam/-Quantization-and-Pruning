# Абляционный эксперимент: поиск оптимального сетапа итеративного структурного прунинга LLM

## Контекст и цель

Предыдущие итерации эксперимента показали, что итеративный структурный прунинг SmolLM-135M работает только в связке LAMP + LoRA fine-tuning: при `ratio = 0.10` PPL упал с 5 893 (baseline Magnitude без fine-tuning) до 31.79 (LAMP + LoRA). Это подтвердило применимость метода, но оставило открытым вопрос: **какие параметры дают лучший баланс между сжатием и качеством**.

Текущий эксперимент (d05) — это **абляция по параметрам**. Цель: зафиксировать базовый сетап, варьировать по одному параметру за раз, найти значения, которые минимизируют PPL при фиксированном коэффициенте прунинга. Итог — рекомендованный конфиг для следующей итерации.

## Сетап

**Модель:** SmolLM-135M (134.5M параметров, fp16, NVIDIA RTX 4080 SUPER).

**Датасет:** WikiText-2. PPL считается на тестовой выборке через скользящее окно (512 токенов, шаг 256). Fine-tuning — на подмножестве train (1000–5000 примеров в зависимости от конфига).

**Стратегия прунинга:** итеративный структурный прунинг MLP-слоёв (`gate_proj`, `up_proj`, `down_proj`). Attention-проекции и эмбеддинги исключены из прунинга из-за GQA (9 query-голов против 3 KV-голов) — синхронное удаление групп голов требует ручной координации, которой `torch-pruning` не делает из коробки.

**Метрики:** PPL (основная), `params`, `model_size_mb`, `peak_mem_mb`, `eval_time_s`, `total_time_s`.

**Базовый конфиг (default):**
- `importance = lamp`
- `steps = 5`
- `finetune_epochs = 2`
- `lora_r = 8`, `lora_alpha = 16`
- `finetune_lr = 1e-4`
- `train_size = 2000`
- `target_ratio = 0.05`

**Группы абляций:**
- `importance`: `[lamp, taylor, magnitude]`
- `target_ratio`: `[0.02, 0.05, 0.10]`
- `steps`: `[3, 5, 10]`
- `finetune_epochs`: `[1, 2, 3]`
- `lora_r`: `[8, 16, 32]`
- `train_size`: `[1000, 2000, 5000]`
- `finetune_lr`: `[5e-5, 1e-4, 2e-4]`

Каждый эксперимент сохраняется в отдельный CSV в `logs/d05/` с именем `<group>=<value>.csv`.

## Ход работы

Реализованы четыре ячейки ноутбука:

1. **Функция итеративного прунинга с LoRA fine-tuning.** На каждом из `steps` шагов: `pruner.step()` удаляет долю MLP-каналов, затем LoRA-адаптеры обучаются `finetune_epochs` эпох на подмножестве WikiText-2 train, после чего `merge_and_unload()` встраивает адаптеры в веса и модель возвращается в `eval()`.

2. **Конфигурация абляций.** `DEFAULT_CONFIG` задаёт базовый сетап, `ABLATION_GROUPS` — сетки значений, `ACTIVE_GROUPS` — какие группы запускать сейчас, `SKIP_EXISTING = True` — не перезапускать уже сохранённые CSV.

3. **Цикл запуска.** Для каждой активной группы последовательно прогоняются все значения, результат сохраняется в CSV, ошибки ловятся и тоже сохраняются с полем `error`.

4. **Загрузка и визуализация.** Собирает все CSV из `logs/d05/`, выводит сводную таблицу, отмечает лучший PPL в каждой группе, строит bar-chart в логарифмической шкале по PPL. В конце — «BEST OVERALL CONFIG» с рекомендованными значениями всех параметров.

## Первые результаты: группа `importance`

Группа `importance` — sanity check, а не оптимизация: нужно подтвердить, что LAMP действительно лучше альтернатив на LLM.

| Importance | PPL @ ratio=0.05 | Params | Status |
|---|---:|---:|---|
| **lamp** | **25.50** | 130 533 696 |  успешно |
| taylor | — | — |  упал |
| magnitude | — | — |  считается |

**LAMP** подтвердил ожидания: PPL 25.50 — сопоставимо с прошлым экспериментом (25.41 при `finetune_epochs=3`, сейчас `finetune_epochs=2`). Параметры уменьшились с 134.5M до 130.5M (3% сжатия, что соответствует 5% удаления только из MLP-подмножества).

**Taylor** упал с `AttributeError: 'NoneType' object has no attribute 'data'`. Причина: `TaylorImportance` — gradient-based критерий, он читает `.grad`-атрибуты параметров, а в коде `pruner.step()` вызывался до первого `loss.backward()`. Градиенты были `None`. Для исправления добавлена функция `calibrate_gradients`, которая перед каждым `pruner.step()` выполняет forward+backward на 3 батчах и заполняет `.grad`. Эксперимент `importance=taylor` будет перезапущен с этой правкой.

**Magnitude** считается. Ожидание: PPL в диапазоне сотен или тысяч — критерий не отражает реальную важность каналов для LLM. Этот результат нужен как контрастный baseline в отчёте.

## Приоритеты запуска

**Фаза 1 — поиск лучшего конфига (5 групп, ~13 прогонов):**
- `lora_r = [8, 16, 32]` — ожидаемое улучшение 2–4 пункта PPL
- `train_size = [1000, 2000, 5000]` — ожидаемое улучшение 2–4 пункта
- `finetune_epochs = [1, 2, 3]` — ожидаемое улучшение 3–5 пунктов

- `target_ratio = [0.02, 0.05, 0.10]` — кривая деградации

**Фаза 2 — предельные улучшения (2 группы, ~6 прогонов):**
- `steps = [3, 5, 10]` — ожидаемое улучшение 1–2 пункта, дорого по времени
- `finetune_lr = [5e-5, 1e-4, 2e-4]` — маргинальный эффект, в пределах шума

## Прогноз итогового результата

Стартовый PPL при `ratio = 0.05` (default `r=8, train_size=2000, epochs=2`): **~25–27**.

После фазы 1 (лучший конфиг `r=32, train_size=5000, epochs=3`): **~21–23**. Это 15–25% от baseline 18.38 — практический результат для структурного прунинга LLM.

После фазы 2 (плюс `steps=10`): **~20–22**. Дальнейшее улучшение ограничено: структурный прунинг принципиально теряет больше качества, чем неструктурированный. Для более амбициозных результатов нужен другой подход — полное fine-tuning вместо LoRA, Wanda, SparseGPT, или переход на модель без GQA с прунингом attention.

## Ограничения текущего сетапа

**Прунинг только MLP-слоёв.** Из-за GQA attention-проекции в `ignored_layers`, поэтому потолок сжатия ниже номинального `ratio`: при 5% удаления MLP-каналов модель уменьшается на 3%, а не на 5%. При `ratio = 0.10` — на 6%, а не 10%.

**LoRA fine-tuning ограничен по ёмкости.** Даже `r=32` даёт около 0.4M обучаемых параметров на 135M модель — это 0.3% от общего числа. Полное fine-tuning восстановило бы больше, но требует в 4–6 раз больше памяти и времени.

**Один seed.** Все прогоны с `SEED = 42`, но LoRA-инициализация и порядок батчей могут давать разброс ±0.5–1.0 пункта PPL. Для строгой валидации нужны 3 прогона с разными seed и усреднение.

**Замеры памяти зашумлены.** `peak_mem_mb` включает фрагментацию PyTorch-аллокатора после LoRA fine-tuning, а не только реальное потребление модели. Для чистых замеров нужна принудительная очистка (`gc.collect()` + `torch.cuda.empty_cache()`) перед `reset_peak_memory_stats()` — она добавлена в код, но baseline-прогоны её не имели, поэтому прямое сравнение пиковой памяти между сетапами некорректно.
